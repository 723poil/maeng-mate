# ADR 0010. macOS 실행과 배포

상태: 채택

## 맥락

개발 환경 밖에서도 앱을 설치하고 로그인 시 기존 기록과 설정으로 실행할 수 있어야 한다.

## 결정

- 개인과 기업이 앱을 수정하고 상업적으로 재배포할 수 있도록 프로젝트 코드와 문서에 MIT 라이선스를 적용한다. 저장소 루트의 `LICENSE`를 원본으로 삼고, Python 패키지와 macOS 앱 번들의 `Contents/Resources/LICENSE`에 같은 파일을 동봉한다. 외부 구성요소는 각 라이선스를 따른다.

- Finder 실행은 앞선 서비스 작업이 끝난 뒤 설치 기록을 확인한다. 시작 준비가 끝나면 메뉴바 프로세스에 메인 창 표시를 요청한다. 반복 요청은 같은 창을 재사용한다. 로그인 자동 시작은 창을 열지 않고 메뉴바 버튼은 기존 빠른 패널을 전환한다. 창을 닫으면 Dock에서 다시 열 수 있고, ⌘Q와 Dock 종료는 화면 프로세스를 종료한다. 이후 앱 번들을 다시 열면 기존 상주 서버를 재사용한다.

- 제품 표시 이름은 Catch다. 앱 번들 `Catch.app`, 창 제목·메뉴, 알림 발신 앱의 기본 이름, DMG 볼륨과 파일 이름 `Catch-<버전>-macOS-arm64.dmg`에 쓴다. 기존 사용자의 기록·자격 정보·자동 실행·MCP 연결을 그대로 쓰도록 번들 식별자 `local.maeng-mate`, 지원 폴더 `MaengMate`, 번들 안의 실행 파일 `MaengMate`, CLI·패키지·스킬·MCP 서버 이름 `maeng-mate`, 백업 확장자 `.maengbackup`과 저장소 주소는 바꾸지 않는다. 앱 내 업데이트는 설치된 번들을 제자리에서 교체하므로 이전 버전에서 올라온 설치는 번들 파일 이름이 `Maeng Mate.app`으로 남을 수 있다. 새 DMG로 직접 설치할 때는 이전 이름의 번들을 응용 프로그램 폴더에서 지운다.

- 앱 번들·DMG의 설치 볼륨·알림 발신 앱의 기본 아이콘은 흰 타일 아래에서 올려다보는 검은 고양이 도안을 공유한다. 원본은 `src/assets/app-icon.svg` 벡터 한 벌이며 사이트의 `site/assets/app-icon.svg`는 같은 파일의 사본이다. 흰 바탕이 밝은 배경에 묻히지 않도록 옅은 그림자와 테두리를 둔다. 메뉴바의 단색 표시는 같은 고양이를 단순화한 템플릿 이미지다([ADR 0005](0005-macos-interface.md)). 빌드에서 배포용 벡터 원본을 일반·Retina 크기의 ICNS로 변환한다.

- 사용자 LaunchAgent 두 개가 상주 서버·메뉴바를 시작한다. 비정상 종료는 복구하고 정상 종료는 다음 로그인이나 명시적 시작까지 유지한다. 역할 잠금과 실행 파일·명령·작업 경로를 확인해 중복 실행과 잘못된 종료를 막는다. 역할별 PID는 잠금 안에서 기록·정리하고, PID 정리가 실패해도 잠금은 해제한다. 메뉴바와 상주 서버는 시작 중 일부만 등록된 종료 신호도 복원한다. plist에는 토큰을 넣지 않는다.
- 소스 실행의 PID 식별은 가상환경 Python의 실제 링크 대상이 `Python.framework/Versions/<버전>/bin/python<버전>`인 macOS 프레임워크이면 같은 버전의 실행 가능한 `Resources/Python.app/Contents/MacOS/Python`도 허용한다. CPython 프레임워크 런처가 해당 앱으로 교체 실행하면서 프로세스 명령의 실행 파일 표현이 바뀌기 때문이다. `src/bootstrap/instance.py`는 일반 Python 경로와 배포 앱의 기존 판정을 유지하고 역할별 전체 명령·작업 폴더 확인을 계속 요구한다. 실제 하위 프로세스 통합 검사로 모듈·콘솔 진입점의 역할 식별과 잘못된 역할·추가 인수·다른 작업 폴더·다른 인터프리터·종료된 PID의 거부를 확인한다. 서비스 수명 검증에는 기존 설치와 지원 폴더·서비스·자격 정보 식별자·포트를 모두 분리한 임시 프로필을 사용하며, 이를 기본 개발 설치본 검증으로 간주하지 않는다.
- 공개키가 있는 배포본은 기존 지원 폴더 `MaengMate`, 기본 포트 43127, 서비스·키체인 식별자 접두사 `local.maeng-mate`를 유지한다. 소스와 공개키 없는 로컬 패키지는 `MaengMateDev`, 43128, `local.maeng-mate.dev`를 사용한다. 각 실행본의 DB·백업·PID·잠금·로그·알림 발신 앱이 분리되며, 처음 개발용을 설치하면 빈 DB와 별도 내부 키로 시작한다. 기존 공유 설치의 기록과 외부 자격 정보는 배포용에 남는다.
- 개발용 설치는 Application Support에 실행본을 준비한다. 배포 앱은 PyInstaller onedir로 Python·의존성·스킬·알림 번들 ZIP을 포함한다. LaunchAgent 등록과 역할 실행은 같은 명령 생성기를 써서 개발 설치 경로의 가상환경 또는 동봉 실행 파일을 선택한다. 메뉴바의 재시작 명령과 역할 실행기는 같은 OS 환경 허용 목록을 사용하며, 역할별 앱 설정은 실행 시에만 추가한다. DMG의 앱을 Applications로 옮긴 뒤 처음 실행하면 자동 실행을 등록한다.
- DB·로그·시작 설정과 수정 가능한 알림 번들은 Application Support에, 비밀값은 Keychain에 둔다. 서명된 배포 앱에는 개인 DB·설정·로그·토큰을 넣지 않는다. 이름·아이콘 적용은 지원 폴더에 압축을 푼 알림 번들에서 수행한다.
- 설치 시 기존 서비스를 종료하고 역할·저장 잠금 안에서 기존 DB를 권한 600으로 백업한 뒤 갱신한다. 개발 설치의 DB 이전과 배포 앱의 백업은 같은 SQLite 백업 함수를 사용한다. 새 파일에 WAL의 커밋까지 복사하고 `quick_check`가 성공해야 사본을 사용한다. 복사 실패 시 새 사본을 정리한다. 설치 완료 표시는 등록과 인증 API 준비를 확인한 뒤에만 남긴다. 설치·시작·재시작 응답은 준비 검사를 통과한 `/v1/status` 응답과 두 역할의 PID를 기준으로 표시한다. 시작 준비는 최대 60초 동안 재확인하며 개별 상태 요청의 제한 시간은 1초다. 별도의 `service status` 요청은 매번 새로 확인한다. 경로가 바뀌거나 빌드가 바뀌면 등록을 갱신한다. 배포 앱의 첫 설치·업데이트에서는 내부 API 키에 한해 필요한 Keychain 승인을 요청한다.
- DMG는 660×400 설치 창에 128pt 아이콘으로 앱을 왼쪽, 응용 프로그램 폴더 링크를 오른쪽에 두고 그 사이에 화살표 배경을 그린다. 창 크기·아이콘 배치·배경은 개발 의존성 `dmgbuild`가 볼륨의 `.DS_Store`에 직접 기록한다. Finder를 스크립트로 조작하지 않으므로 화면 세션이 없는 CI에서도 같은 결과가 나온다. 배경은 빌드 때 AppKit으로 일반·Retina 크기를 그려 저장소에 이진 파일을 두지 않는다. Finder의 항목 이름이 밝은 모드에서는 검정, 어두운 모드에서는 흰색이므로 배경은 둘 다 읽히는 중간 밝기를 쓴다. 구현은 `packaging/build.py`의 `build_background`와 `build_dmg` 호출이다.
- `mise run package`는 `dist/`에 .app·DMG·SHA256을 만든다. 현재 배포 대상은 Apple Silicon과 macOS 26 이상이다. 환경 변수 `CODESIGN_IDENTITY`에 키체인의 Developer ID Application 인증서 이름을 주면 앱·동봉 알림 앱·DMG를 그 인증서로 서명하고, 비어 있으면 임시(ad hoc) 서명으로 빌드한다.
- Developer ID 서명은 공증 조건에 맞춰 강화 런타임과 보안 타임스탬프를 적용한다. 바깥 서명이 안쪽 코드의 해시를 담으므로 Mach-O 파일, 깊은 내부 번들, 앱 순서로 서명하고 `--deep` 일괄 서명은 쓰지 않는다. 내부 구성요소에 원래 부여된 권한은 유지하고 앱에는 별도 권한(entitlements)을 추가하지 않는다. 알림 앱은 압축해 동봉하기 전에 서명한다. 설치 뒤 이름·아이콘을 바꾼 알림 앱은 기존처럼 사용자 Mac에서 임시 서명으로 다시 서명한다. DMG 서명은 체크섬과 업데이트 피드 계산보다 먼저 수행한다. 구현은 `packaging/build.py`의 `sign`이다.
- 환경 변수 `NOTARY_PROFILE`에 `xcrun notarytool store-credentials`로 키체인에 저장한 프로필 이름을 주면 서명한 DMG를 Apple 공증에 제출하고 결과를 기다린다. 제출 명령이 성공해도 심사 결과가 `Accepted`가 아니면 빌드를 실패시키고 상태와 제출 ID를 출력한다. 승인되면 DMG에 공증 표를 스테이플한 뒤 체크섬을 계산한다. Developer ID 서명 없이 공증을 요청하면 시작 전에 멈춘다.
- 릴리스 워크플로의 `package` 작업은 `production` 환경 시크릿으로 서명·공증한다. `DEVELOPER_ID_P12_BASE64`·`DEVELOPER_ID_P12_PASSWORD`에는 개인키를 포함해 내보낸 Developer ID Application 인증서를, `NOTARY_API_KEY_BASE64`·`NOTARY_API_KEY_ID`에는 App Store Connect API 키를 넣는다. 팀 API 키라면 `NOTARY_API_ISSUER_ID`도 넣는다. 작업은 임의 비밀번호의 임시 키체인을 기본 키체인으로 만들어 인증서와 공증 프로필을 넣고, 인증서·키 파일은 넣은 직후 지운다. 그 다음 `CODESIGN_IDENTITY`와 `NOTARY_PROFILE`을 빌드에 넘긴다. 시크릿이 없으면 임시 서명본을 게시하지 않고 멈춘다. 게시 전 검증은 DMG의 공증 표 스테이플과 동봉 앱의 Apple 공증 등록을 확인하며, 작업이 끝나면 임시 키체인을 지운다. 0.12.0까지 게시한 DMG는 임시 서명이라 처음 내려받으면 Gatekeeper가 차단한다. Sparkle 규칙상 EdDSA 키를 유지하면 코드 서명 인증서를 바꿀 수 있으므로 기존 설치본도 앱 내 업데이트로 공증된 버전을 받는다. 실제 업데이트 경로는 첫 공증 릴리스에서 확인한다.
- 앱 버전은 `pyproject.toml`의 `project.version`에서 관리한다. 설정의 ‘앱 정보’ 페이지는 설치한 패키지의 버전을 표시한다. 배포 빌드는 같은 번호를 앱 번들과 DMG 이름에 쓰고, 동봉 실행 파일이 읽은 버전이 다르면 DMG 생성을 중단한다.
- GitHub 릴리스마다 배포 커밋에 `v<주 버전>.<부 버전>.<패치 버전>` 형식의 주석 태그를 붙인다. `v` 뒤의 숫자는 해당 커밋의 `project.version`과 일치해야 한다. 호환성을 깨는 변경은 주 버전, 호환되는 기능 추가는 부 버전, 호환되는 수정과 성능 개선은 패치 버전을 올린다. 첫 태그는 현재 앱 버전에 맞춘 `v0.2.0`이다.
- 공개한 태그는 같은 커밋에 유지한다. 배포 후 수정 사항은 새 버전으로 게시한다. GitHub 릴리스에는 사용자에게 달라진 점을 한국어로 적고, 해당 커밋에서 만든 DMG와 SHA-256 체크섬 파일을 첨부한다.

### 공개 설치 사이트

- 앱 소개·다운로드 화면의 공개 파일은 `site/`에서 관리한다. Sites 전용 저장소에는 이를 `public/`으로 동기화하고 `packaging/site/`의 빌드·요청 처리 파일도 복사한다. `node packaging/site/build.mjs public dist/server/index.js`로 공개 파일을 포함한 읽기 전용 Worker를 만들고 앱과 독립적으로 배포한다.
- 사이트의 `/latest-appcast.xml`은 GitHub 최신 릴리스의 공개 Sparkle 피드 한 곳만 읽어 전달한다. 페이지를 열면 피드에 기록된 버전과 Apple Silicon DMG 주소를 대조해 다운로드 버튼 세 곳, 버전 표기와 릴리스 안내를 함께 갱신한다. 피드는 최대 1분 캐시한다. 사이트 재배포나 GitHub 쓰기 권한이 필요 없고, 자바스크립트 또는 피드를 사용할 수 없으면 GitHub 최신 릴리스 페이지에서 내려받는다.
- 제목은 기기에 설치된 Apple SD Gothic Neo를 사용하고, 해당 글꼴이 없으면 본문과 같은 Pretendard를 사용한다. Pretendard v1.3.9 가변 웹폰트와 SIL Open Font License 고지는 `site/assets/fonts/`에 함께 둔다.
- 소개 페이지는 상단 탐색과 다운로드를 먼저 찾을 수 있도록 넓은 화면에는 텍스트 링크를, 좁은 화면에는 펼침 메뉴를 둔다. 밝은 제품 소개 영역에 검은 캡슐형 다운로드 버튼과 화면 선택기를 배치한다. 연동 기능과 설치 안내는 검은 배경 위의 카드와 접이식 질문 목록으로 구분한다. 화면 선택과 설치 안내는 브라우저의 라디오 버튼과 details를 사용해 키보드로도 조작할 수 있다.
- 소개 첫 화면의 설정 예시는 반투명 사이드바와 불투명한 앱 정보 본문으로 구성한다. 사이트 브랜드에는 배포 앱 아이콘을, 메뉴바 열기 버튼에는 앱의 단색 고양이 도안을 사용한다.
- 메뉴바·캘린더·출퇴근 기록은 예시 데이터를 넣은 AppKit 뷰에서 글자와 컨트롤을 투명 WebP로 렌더링한다. 사이트의 유리 효과는 이 이미지 아래에 배경 흐림을 적용해 표현한다. 원본 크기 링크는 같은 소재와 배경을 합성한 독립 이미지를 연다. 개인 데스크톱이나 운영 DB는 사용하지 않는다. 사이트 변경은 좁은 화면과 넓은 화면에서 이미지 확대, 메뉴바 열기·닫기, 설치 안내 및 다운로드 주소를 확인한다.

### 앱 내 업데이트

메뉴바가 시작되면 자동 조회를 활성화한다. 공개 배포본은 Sparkle의 기본 하루 주기를 따르고, 개발 실행본과 공개키 없는 패키지는 시작 시와 이후 24시간마다 확인한다. 자동 조회는 새 버전을 발견했을 때만 안내한다. 설정 ‘앱 정보’의 **업데이트 확인…**으로 직접 확인하면 최신 버전 여부나 조회 오류도 표시한다. 공개 배포본은 Sparkle 2의 기본 창으로 변경 내용과 설치 여부를 표시하고 설치 후 앱을 다시 연다. 화면 프로세스는 일반 macOS 앱으로 Dock에 표시한다. 업데이트 창이 닫힌 뒤에도 같은 Dock 아이콘을 유지한다. 개발 실행본과 공개키 없이 만든 로컬 패키지는 GitHub의 최신 정식 태그를 조회하고 새 버전이 있으면 릴리스 페이지로 안내한다. 이 두 실행 방식은 화면에 ‘개발용’으로 표시한다. 개발 앱의 새 버전 안내에는 현재 개발용 버전과 내려받을 최신 버전 번호를 함께 적는다. 자체 업데이트 도입 전 버전에서는 새 DMG를 한 번 설치해야 한다.

- `project.version`을 번들의 `CFBundleVersion`과 표시 버전에 함께 쓴다. Sparkle은 고정 HTTPS 주소 `releases/latest/download/appcast.xml`에서 피드를 받고 버전별 릴리스의 DMG를 검증한다. 서명된 피드와 압축 해제 전 Ed25519 검증을 사용한다. Apple Developer ID와 공증은 기존 배포 정책을 따른다.
- 배포 담당자는 Sparkle 공식 `generate_keys --account maeng-mate`로 앱 전용 키를 한 번 생성하고 안전하게 보관한다. 공개키는 GitHub Actions의 `production` 환경 변수 `SPARKLE_PUBLIC_ED_KEY`에, 같은 계정의 `generate_keys -x`로 내보낸 개인키는 같은 환경의 시크릿 `SPARKLE_PRIVATE_ED_KEY`에 등록한다. 내보낼 때도 같은 `--account maeng-mate`를 지정한다. 이후 릴리스에서도 같은 키를 사용한다.
- `packaging/sparkle_release.py`는 고정된 공식 아카이브의 SHA-256을 확인한다. 빌드에는 프레임워크·라이선스·공개키를 넣고, 서명 단계에서만 개인키를 표준 입력으로 전달한다. 이번 릴리스의 DMG와 한국어 노트로 피드를 생성하고 버전·파일·서명을 검증한 뒤 DMG·체크섬·피드를 한 릴리스로 공개한다.
- 확인·다운로드 중에는 상주 서버를 유지한다. 설치를 위해 메뉴바를 종료할 때 편집·복원 작업을 확인한 뒤 상주 역할을 내린다. Sparkle이 앱을 교체하고 다시 열면 기존 배포 앱 설치 경로가 DB 백업, 서비스 재등록과 인증 API 준비 확인을 수행한다.
- 검증에는 임시 키와 운영 앱과 다른 식별자의 번들을 사용한다. 하위 버전에서 확인·설치한 뒤 새 버전으로 재실행되는지, 서명이 맞지 않으면 설치 전에 멈추는지 확인한다.

### 사용자 백업과 전체 복원

사용자는 설정의 **백업하기**에서 저장 위치를 고르고, **백업 불러오기**에서 백업 시점의 기록과 설정을 함께 복원한다. 전체 복원은 같은 날짜에 정정한 기록과 삭제한 설정까지 선택한 시점으로 되돌린다.

- 백업 파일 하나에 버전·생성 시각과 함께 SQLite 업무 데이터, 앱 설정, 별도 근무 규칙 파일의 존재 여부와 내용을 담는다. DB 사본은 기존 `copy_database`로 만든다. 현재 Mac의 설치 경로와 포트는 시작 설정에서, 관리자 키와 Notion·Slack 토큰은 Keychain에서 계속 읽는다. MCP 접근 권한은 기기별로 관리해 이전에 폐기한 인증 정보가 복원으로 다시 활성화되는 일을 막는다.
- `src/application/data_backup.py`의 백업 동작 계약은 파일 선택 결과를 문자열 값으로 받는다. presentation은 선택한 경로를 그대로 전달하고, bootstrap의 내보내기·미리보기 구현이 `Path`로 변환한다. 복원 도우미 요청도 같은 문자열을 표준 입력으로 전달한다. application에 파일 시스템 타입이나 I/O 의존을 두지 않고 기존 백업 형식·오류 변환·미리보기 지문과 복원 확인 절차를 유지한다. 계층 검사와 임시 DB의 백업·미리보기·복원 준비로 경계를 확인한다.
- 수동 백업은 파일 내용을 `fsync`한 뒤 기존 파일을 덮지 않는 연산으로 게시하고, 임시 게시 폴더를 정리한 다음 대상 디렉터리를 `fsync`해야 성공을 반환한다. 디렉터리 동기화가 지원되지 않는 볼륨의 `EINVAL`·`ENOTSUP`·`EOPNOTSUPP`만 허용해 외장 볼륨 저장을 유지한다. 이 경우 이름의 영속성은 보장하지 않는다. 게시 후 실제 동기화·정리 오류는 `BackupPublicationError`로 구분하고 완성된 파일을 보존한다. 내보내기 화면에는 파일이 생성됐으나 저장 완료를 확인하지 못했음을 알리고 기존 파일 확인과 새 이름 재시도를 안내한다. 임시 DB의 실제 백업·반입, 동기화 호출 순서, 오류 주입과 기존 파일 보호로 검증하며 실제 전원 손실 검증을 대신하지 않는다.
- 불러오면 임시 위치에서 파일 구성·버전·DB 무결성·앱 스키마·근무 규칙을 먼저 검사한다. 화면에 백업 시각과 덮어쓸 범위를 표시하고 사용자가 확인한 뒤 서비스를 멈춘다. 저장 잠금 안에서 현재 데이터를 같은 형식의 복구용 백업으로 보존한 다음 DB와 근무 규칙을 교체한다. 근무 규칙 파일이 없던 시점도 그대로 복원한다.
- 교체 단계를 디스크에 기록하고 재시작 시 두 파일의 상태가 확정된 뒤에만 서비스가 데이터를 연다. 교체 중 중단되거나 복원본으로 서비스를 준비하지 못하면 직전 백업으로 돌아간다. 시험 기동 중에는 관리자 인증을 거친 상태 조회만 열고 수집과 알림 전달을 보류한다. 독립 복원 도우미가 두 역할과 API의 준비를 확인한 뒤 확정한다. 도우미가 이때 종료되면 상주 서버가 복구를 요청한다.
- `src/infrastructure/data_backup.py`와 `sqlite/portable_backup.py`는 현재 스키마로 업무 행을 옮겨 휴대용 DB를 만들며, 형식 1은 최대 8 GiB DB를 지원한다. `src/bootstrap/backup_transaction.py`는 직전 백업과 기기 접근 권한을 포함한 비공개 복구 사본을 만들고, `backup_restore.py`가 서비스와 잠금을 관리한다. 시각이 지났거나 발송을 시작했던 미확정 알림은 재발송을 방지하기 위해 결과 미확인으로 마감한다.
- 설치 전 DB와 복원 전 이동용 백업은 종류별 최근 세 개를 생성 순서대로 보관한다. 한 번 더 되돌릴 여유를 두면서 반복 작업에 따른 저장 공간 증가를 제한한다. `backup_retention.py`가 서비스 관리 잠금 안에서 종류별 생성 기록을 관리한다. 설치 완료 표시 저장 또는 복원 확정이 끝나야 해당 종류를 정리한다. 실패·재시작 롤백 중에는 정리하지 않으며 다음 성공 때 다시 적용한다. 진행 중 복원의 비공개 복구 사본은 이 기록에 포함하지 않는다.
- 설치용 SQLite 사본은 비공개 폴더에서 완성해 비어 있는 공개 이름에 하드 링크로 게시한다. 설치·복원 사본 모두 독점 생성 때 연 파일 핸들에서 기기·inode·변경 시각·크기를 읽어 종류별 생성 기록에 남긴다. 경로를 다시 조회해 등록했던 이전 기록, 수동 내보내기, 수정·교체한 파일과 링크는 보존한다. 기록 파일도 같은 핸들로 읽고 갱신한다. 기록이 손상되면 사본을 보존한다.
- 정리 시 `backup_retention.py`는 등록된 만료 항목 하나를 macOS의 독점 이름 변경으로 앱 지원 폴더의 종류별 비공개 대기 폴더(`.pre-install-retiring`, `.pre-restore-retiring`)로 옮긴다. 이동한 이름에 원래 이름·생성 기록·파일 생성 시각·수정 시각을 함께 담아 이동 자체가 재시도에 필요한 기록이 된다. 서비스 관리 잠금 안에서 해당 폴더의 권한과 소유자를 확인하고, 생성 기록과 실제 파일이 일치하면 대기 폴더의 링크 하나만 제거한다. 다른 하드 링크에 저장된 내용과 공개 이름으로 다시 저장된 파일은 보존한다.
- 종류별로 대기 항목 하나를 마쳐야 다음 항목을 옮긴다. 이동과 제거 시 디렉터리를 동기화하며 중단되면 다음 같은 종류의 성공 시 미완료 항목부터 처리한다. 이동된 파일이 교체·수정된 경우 원래 이름이 비어 있을 때만 되돌린다. 이름 충돌, 출처를 확인할 수 없는 대기 항목, 독점 이동 미지원 시에는 파일을 보존하고 정리를 보류한다.
- 이 보장은 앱이 서비스 관리 잠금을 지키고 소유자 전용 대기 폴더를 단독으로 관리하는 범위에 적용한다. 같은 사용자 권한의 다른 프로세스가 그 폴더나 생성 기록을 직접 바꾸는 경우까지 보장하지 않는다. 세 개는 정상 정리가 끝난 종류별 관리 사본 수이며, 수동 파일·기존 사본·보류된 항목을 포함한 디스크 사용량에는 상한이 없다.
- 임시 앱 디렉터리의 실제 SQLite·이동용 백업으로 확정·실패·재시작 롤백과 수동 백업 보존을 확인한다. 정리 단계에 오류를 주입해 재시도 전후의 대기 항목 수, 다른 하드 링크의 바이트, 공개 이름 재사용 및 충돌 해소 후 복구를 확인한다.
- 구현 검증에는 임시 앱 디렉터리를 사용한다. 백업 뒤 기록과 근무 규칙을 변경하고 복원해 값이 돌아오는지 확인한다. 취소, 손상된 파일, 호환되지 않는 형식, 교체 중 종료, 근무 규칙 파일 부재와 접근 토큰 폐기 상태도 확인한다.
- 휴대용 DB는 v17·v18·v19를 지원한다. `sqlite/schema_versions.py`에 출시한 버전별 기준 DDL과 다음 버전으로의 변환을 보존한다. 읽기 전용 사본의 전체 SQLite 카탈로그를 앱이 만든 기준과 대조한 뒤 버전 이력·무결성·기기 권한 부재를 검사한다. 임시 복원본에는 v17→v18에서 상태 선택값 테이블을, v18→v19에서 기기별 목록 권한 테이블을 추가하고 버전 이력과 함께 한 트랜잭션으로 확정한다. 기존 업무 기록은 유지하며 상태 선택값은 다음 정상 수집에서 채운다.

### 릴리스 브랜치와 GitHub Actions

1. 원격 `main`에서 `release/<후보 버전>` 브랜치를 만들고 배포할 변경을 모은다. 직전 배포 태그와 비교해 기존 사용자가 설정·데이터·MCP 연결을 그대로 쓸 수 있는지, 새로 쓸 수 있는 기능이 있는지 확인한다. 여러 변경이 있으면 가장 큰 변경을 기준으로 주·부·패치 버전 중 하나를 올리고 하위 번호를 0으로 되돌린다. 문서만 고쳐 앱을 배포할 필요가 없을 때는 일반 PR로 병합한다.
2. 릴리스 브랜치에서 `project.version`과 `uv.lock`을 갱신한다. `docs/releases/<버전>.md`에는 사용자가 체감할 변화만 골라 짧은 한국어 앱 릴리스 노트로 쓴다. 새로 할 수 있는 일은 ‘새로운 기능’, 기존 사용 경험의 변화는 ‘개선 사항’, 고친 증상은 ‘오류 수정’에 적는다. 해당하는 항목만 쓰고 각 항목은 사용자가 하는 일이나 겪던 증상으로 설명한다. 지원 환경과 설치 안내는 저장소 README에서 관리하며 릴리스 본문에서 생략한다. 버전 선택의 근거, 호환성, 검증 결과는 PR 본문에 적는다.
3. `main`을 대상으로 [릴리스 PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE/release.md)에 맞춰 PR을 연다. 제목은 `Catch <버전> 릴리스`로 쓰고 본문은 변경 사항, 호환성, 검증 순서로 작성한다. 이번 버전에서 해결하는 이슈는 본문 끝에 `Closes #번호`로 한 줄씩 연결한다. GitHub Actions는 macOS 26 arm64에서 후보 버전·잠금 파일·노트를 확인하고 정적 검사와 MCP stdio 통합 검사를 실행한다. 검토 중 변경이 생기면 같은 PR에서 다시 검증한다.
4. 검토와 검사가 끝나면 PR을 병합한다. `main` 푸시를 받은 워크플로는 해당 SHA가 같은 저장소의 릴리스 PR을 병합한 커밋인지 확인한다. 그 커밋의 검사가 통과하면 `package` 작업이 `production` 환경에서 같은 커밋의 앱과 DMG를 Developer ID로 서명·공증해 빌드하고 업데이트 피드에 서명한다. 환경의 배포 허용 브랜치는 `main`으로 설정한다. 체크섬을 확인하고 DMG를 읽기 전용으로 열어 서명·공증과 동봉 앱 실행을 검증한 뒤 그 커밋에 주석 태그를 붙인다. 검토한 노트, DMG, 체크섬과 서명된 피드를 GitHub Release에 게시한다. 배포가 중단되면 해당 병합 실행을 재시도한다. 이미 공개한 릴리스는 그대로 유지한다.

## 결과와 검증

설치 후 Python·uv·mise 없이 실행한다. `src/bootstrap/service.py`, `packaged_app.py`, `packaging/app.spec`, `packaging/build.py`에서 구현한다. 배포 점검은 동봉 실행 파일의 `--check`와 DMG 읽기 전용 탑재를 사용한다. 임시 DB와 루프백 API·MCP·알림 번들을 점검한다. 스킬은 임시 홈에 Codex와 Claude Code 양쪽으로 설치한 뒤 지침과 UI 메타데이터가 동봉 파일과 일치하는지 확인한다.
