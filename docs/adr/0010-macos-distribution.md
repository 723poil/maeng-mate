# ADR 0010. macOS 실행과 배포

상태: 채택

## 맥락

개발 환경 밖에서도 앱을 설치하고 로그인 시 기존 기록과 설정으로 실행할 수 있어야 한다.

## 결정

- 앱 번들과 DMG의 설치 볼륨은 메뉴바의 수첩·체크 도안을 청록색 바탕에 얹은 아이콘을 공유한다. 빌드에서 배포용 벡터 원본을 일반·Retina 크기의 ICNS로 변환한다.

- 사용자 LaunchAgent 두 개가 상주 서버·메뉴바를 시작한다. 비정상 종료는 복구하고 정상 종료는 다음 로그인이나 명시적 시작까지 유지한다. 역할 잠금과 실행 파일·명령·작업 경로를 확인해 중복 실행과 잘못된 종료를 막는다. 역할별 PID는 잠금 안에서 기록·정리하고, PID 정리가 실패해도 잠금은 해제한다. 메뉴바와 상주 서버는 시작 중 일부만 등록된 종료 신호도 복원한다. plist에는 토큰을 넣지 않는다.
- 개발용 설치는 Application Support에 실행본을 준비한다. 배포 앱은 PyInstaller onedir로 Python·의존성·스킬·알림 번들을 포함한다. LaunchAgent 등록과 역할 실행은 같은 명령 생성기를 써서 개발 설치 경로의 가상환경 또는 동봉 실행 파일을 선택한다. 메뉴바의 재시작 명령과 역할 실행기는 같은 OS 환경 허용 목록을 사용하며, 역할별 앱 설정은 실행 시에만 추가한다. DMG의 앱을 Applications로 옮긴 뒤 처음 실행하면 자동 실행을 등록한다.
- DB·로그·시작 설정과 수정 가능한 알림 번들은 Application Support에, 비밀값은 Keychain에 둔다. 서명된 배포 앱에는 개인 DB·설정·로그·토큰을 넣지 않는다. 이름·아이콘 적용은 지원 폴더에 복사한 알림 번들에서 수행한다.
- 설치 시 기존 서비스를 종료하고 역할·저장 잠금 안에서 기존 DB를 권한 600으로 백업한 뒤 갱신한다. 개발 설치의 DB 이전과 배포 앱의 백업은 같은 SQLite 백업 함수를 사용한다. 새 파일에 WAL의 커밋까지 복사하고 `quick_check`가 성공해야 사본을 사용한다. 복사 실패 시 새 사본을 정리한다. 설치 완료 표시는 등록과 인증 API 준비를 확인한 뒤에만 남긴다. 설치·시작·재시작 응답은 준비 검사를 통과한 `/v1/status` 응답과 두 역할의 PID를 기준으로 표시한다. 시작 준비는 최대 60초 동안 재확인하며 개별 상태 요청의 제한 시간은 1초다. 별도의 `service status` 요청은 매번 새로 확인한다. 경로가 바뀌거나 빌드가 바뀌면 등록을 갱신한다. 배포 앱의 첫 설치·업데이트에서는 내부 API 키에 한해 필요한 Keychain 승인을 요청한다.
- `mise run package`는 `dist/`에 .app·DMG·SHA256을 만든다. 현재 배포 대상은 Apple Silicon과 macOS 26 이상이며 로컬 개발 서명을 사용한다. Apple 배포 공증은 적용하지 않았다.
- 앱 버전은 `pyproject.toml`의 `project.version`에서 관리한다. 설정 사이드바 하단은 설치한 패키지의 버전을 표시한다. 배포 빌드는 같은 번호를 앱 번들과 DMG 이름에 쓰고, 동봉 실행 파일이 읽은 버전이 다르면 DMG 생성을 중단한다.
- GitHub 릴리스마다 배포 커밋에 `v<주 버전>.<부 버전>.<패치 버전>` 형식의 주석 태그를 붙인다. `v` 뒤의 숫자는 해당 커밋의 `project.version`과 일치해야 한다. 호환성을 깨는 변경은 주 버전, 호환되는 기능 추가는 부 버전, 호환되는 수정과 성능 개선은 패치 버전을 올린다. 첫 태그는 현재 앱 버전에 맞춘 `v0.2.0`이다.
- 공개한 태그는 같은 커밋에 유지한다. 배포 후 수정 사항은 새 버전으로 게시한다. GitHub 릴리스에는 사용자에게 달라진 점을 한국어로 적고, 해당 커밋에서 만든 DMG와 SHA-256 체크섬 파일을 첨부한다.

### 공개 설치 사이트

- 앱 소개와 다운로드 화면은 `site/index.html`과 `site/style.css`에서 관리한다. 공개 사이트는 앱과 독립적으로 배포한다. Sites 배포본의 `dist/`에는 `site/`의 정적 파일만 복사한다.
- 다운로드 버튼과 릴리스 노트는 같은 버전을 가리킨다. 새 DMG가 공개되면 GitHub Release의 실제 자산 주소와 버전 표기를 함께 갱신한다. 최신 릴리스 링크는 별도로 유지한다.
- 사이트의 제목은 네이버 마루 부리 SemiBold, 본문과 조작 요소는 Pretendard v1.3.9 가변 웹폰트를 사용한다. 두 글꼴 모두 자체 제공하며 공식 배포 파일과 각 글꼴의 저작권·SIL Open Font License 고지를 `site/assets/fonts/`에 함께 둔다.
- 메뉴바·캘린더·출퇴근 기록은 예시 데이터를 넣은 AppKit 뷰에서 글자와 컨트롤을 투명 WebP로 렌더링한다. 사이트의 유리 효과는 이 이미지 아래에 배경 흐림을 적용해 표현한다. 원본 크기 링크는 같은 소재와 배경을 합성한 독립 이미지를 연다. 개인 데스크톱이나 운영 DB는 사용하지 않는다. 사이트 변경은 좁은 화면과 넓은 화면에서 이미지 확대, 메뉴바 열기·닫기, 설치 안내 및 다운로드 주소를 확인한다.

### 앱 내 업데이트

설정 사이드바의 **업데이트 확인…**에서 사용자가 직접 새 버전을 확인한다. 공개 배포본은 Sparkle 2의 기본 창으로 변경 내용과 설치 여부를 표시하고 설치 후 앱을 다시 연다. 개발 실행본과 공개키 없이 만든 로컬 패키지는 GitHub의 최신 정식 태그를 조회하고 새 버전이 있으면 릴리스 페이지로 안내한다. 자체 업데이트 도입 전 버전에서는 새 DMG를 한 번 설치해야 한다.

- `project.version`을 번들의 `CFBundleVersion`과 표시 버전에 함께 쓴다. Sparkle은 고정 HTTPS 주소 `releases/latest/download/appcast.xml`에서 피드를 받고 버전별 릴리스의 DMG를 검증한다. 서명된 피드와 압축 해제 전 Ed25519 검증을 사용한다. Apple Developer ID와 공증은 기존 배포 정책을 따른다.
- 배포 담당자는 Sparkle 공식 `generate_keys --account maeng-mate`로 앱 전용 키를 한 번 생성하고 안전하게 보관한다. 공개키는 GitHub Actions의 `production` 환경 변수 `SPARKLE_PUBLIC_ED_KEY`에, 같은 계정의 `generate_keys -x`로 내보낸 개인키는 같은 환경의 시크릿 `SPARKLE_PRIVATE_ED_KEY`에 등록한다. 내보낼 때도 같은 `--account maeng-mate`를 지정한다. 이후 릴리스에서도 같은 키를 사용한다.
- `packaging/sparkle_release.py`는 고정된 공식 아카이브의 SHA-256을 확인한다. 빌드에는 프레임워크·라이선스·공개키를 넣고, 서명 단계에서만 개인키를 표준 입력으로 전달한다. 이번 릴리스의 DMG와 한국어 노트로 피드를 생성하고 버전·파일·서명을 검증한 뒤 DMG·체크섬·피드를 한 릴리스로 공개한다.
- 확인·다운로드 중에는 상주 서버를 유지한다. 설치를 위해 메뉴바를 종료할 때 편집·복원 작업을 확인한 뒤 상주 역할을 내린다. Sparkle이 앱을 교체하고 다시 열면 기존 배포 앱 설치 경로가 DB 백업, 서비스 재등록과 인증 API 준비 확인을 수행한다.
- 검증에는 임시 키와 운영 앱과 다른 식별자의 번들을 사용한다. 하위 버전에서 확인·설치한 뒤 새 버전으로 재실행되는지, 서명이 맞지 않으면 설치 전에 멈추는지 확인한다.

### 사용자 백업과 전체 복원

사용자는 설정의 **백업하기**에서 저장 위치를 고르고, **백업 불러오기**에서 백업 시점의 기록과 설정을 함께 복원한다. 전체 복원은 같은 날짜에 정정한 기록과 삭제한 설정까지 선택한 시점으로 되돌린다.

- 백업 파일 하나에 버전·생성 시각과 함께 SQLite 업무 데이터, 앱 설정, 별도 근무 규칙 파일의 존재 여부와 내용을 담는다. DB 사본은 기존 `copy_database`로 만든다. 현재 Mac의 설치 경로와 포트는 시작 설정에서, 관리자 키와 Notion·Slack 토큰은 Keychain에서 계속 읽는다. MCP 접근 권한은 기기별로 관리해 이전에 폐기한 인증 정보가 복원으로 다시 활성화되는 일을 막는다.
- 불러오면 임시 위치에서 파일 구성·버전·DB 무결성·앱 스키마·근무 규칙을 먼저 검사한다. 화면에 백업 시각과 덮어쓸 범위를 표시하고 사용자가 확인한 뒤 서비스를 멈춘다. 저장 잠금 안에서 현재 데이터를 같은 형식의 복구용 백업으로 보존한 다음 DB와 근무 규칙을 교체한다. 근무 규칙 파일이 없던 시점도 그대로 복원한다.
- 교체 단계를 디스크에 기록하고 재시작 시 두 파일의 상태가 확정된 뒤에만 서비스가 데이터를 연다. 교체 중 중단되거나 복원본으로 서비스를 준비하지 못하면 직전 백업으로 돌아간다. 시험 기동 중에는 관리자 인증을 거친 상태 조회만 열고 수집과 알림 전달을 보류한다. 독립 복원 도우미가 두 역할과 API의 준비를 확인한 뒤 확정한다. 도우미가 이때 종료되면 상주 서버가 복구를 요청한다.
- `src/infrastructure/data_backup.py`와 `sqlite/portable_backup.py`는 현재 스키마로 업무 행을 옮겨 휴대용 DB를 만들며, 형식 1은 최대 8 GiB DB를 지원한다. `src/bootstrap/backup_transaction.py`는 직전 백업과 기기 접근 권한을 포함한 비공개 복구 사본을 만들고, `backup_restore.py`가 서비스와 잠금을 관리한다. 시각이 지났거나 발송을 시작했던 미확정 알림은 재발송을 방지하기 위해 결과 미확인으로 마감한다.
- 구현 검증에는 임시 앱 디렉터리를 사용한다. 백업 뒤 기록과 근무 규칙을 변경하고 복원해 값이 돌아오는지 확인한다. 취소, 손상된 파일, 호환되지 않는 형식, 교체 중 종료, 근무 규칙 파일 부재와 접근 토큰 폐기 상태도 확인한다.

### 릴리스 브랜치와 GitHub Actions

1. 원격 `main`에서 `release/<후보 버전>` 브랜치를 만들고 배포할 변경을 모은다. 직전 배포 태그와 비교해 기존 사용자가 설정·데이터·MCP 연결을 그대로 쓸 수 있는지, 새로 쓸 수 있는 기능이 있는지 확인한다. 여러 변경이 있으면 가장 큰 변경을 기준으로 주·부·패치 버전 중 하나를 올리고 하위 번호를 0으로 되돌린다. 문서만 고쳐 앱을 배포할 필요가 없을 때는 일반 PR로 병합한다.
2. 릴리스 브랜치에서 `project.version`과 `uv.lock`을 갱신한다. `docs/releases/<버전>.md`에는 사용자가 체감할 변화만 골라 짧은 한국어 앱 릴리스 노트로 쓴다. 새로 할 수 있는 일은 ‘새로운 기능’, 기존 사용 경험의 변화는 ‘개선 사항’, 고친 증상은 ‘오류 수정’에 적는다. 해당하는 항목만 쓰고 각 항목은 사용자가 하는 일이나 겪던 증상으로 설명한다. 지원 환경과 설치 안내는 저장소 README에서 관리하며 릴리스 본문에서 생략한다. 버전 선택의 근거, 호환성, 검증 결과는 PR 본문에 적는다.
3. `main`을 대상으로 PR을 연다. GitHub Actions는 macOS 26 arm64에서 후보 버전·잠금 파일·노트를 확인하고 정적 검사와 MCP stdio 통합 검사를 실행한다. 검토 중 변경이 생기면 같은 PR에서 다시 검증한다.
4. 검토와 검사가 끝나면 PR을 병합한다. `main` 푸시를 받은 워크플로는 해당 SHA가 같은 저장소의 릴리스 PR을 병합한 커밋인지 확인한다. 그 커밋의 검사가 통과하면 `package` 작업이 `production` 환경에서 같은 커밋의 앱과 DMG를 빌드하고 업데이트 피드에 서명한다. 환경의 배포 허용 브랜치는 `main`으로 설정한다. 체크섬을 확인하고 DMG를 읽기 전용으로 열어 서명과 동봉 앱 실행을 검증한 뒤 그 커밋에 주석 태그를 붙인다. 검토한 노트, DMG, 체크섬과 서명된 피드를 GitHub Release에 게시한다. 배포가 중단되면 해당 병합 실행을 재시도한다. 이미 공개한 릴리스는 그대로 유지한다.

## 결과와 검증

설치 후 Python·uv·mise 없이 실행한다. `src/bootstrap/service.py`, `packaged_app.py`, `packaging/app.spec`, `packaging/build.py`에서 구현한다. 배포 점검은 동봉 실행 파일의 `--check`와 DMG 읽기 전용 탑재를 사용한다. 임시 DB와 루프백 API·MCP·알림 번들을 점검한다. 스킬은 임시 홈에 Codex와 Claude Code 양쪽으로 설치한 뒤 지침과 UI 메타데이터가 동봉 파일과 일치하는지 확인한다.
