# ADR 0002. Notion 수집과 예약

상태: 채택

## 맥락

Notion 표의 속성 구성과 일정 분류는 소스마다 다르다. 도중에 페이지 조회가 실패해도 마지막으로 완성된 자료와 수집 예약이 보존되어야 한다.

## 결정

- 소스별 속성 ID로 업무·일정·휴가를 내부 모델로 정규화한다. 목록 소스에서 차시별 수집을 선택하면 `roundTitleProperty`를 사용해 하위 표를 읽고 부모 소스 단위로 한 번에 확정한다. 원본 항목 ID·URL·수정 시각·차시를 보존한다.
- `수집 소스`에서 Notion 원본 표 주소나 데이터 소스 ID를 입력하고 칼럼을 조회한다. 페이지 안에 여러 원본 표가 있으면 수집할 표를 고른다. 일반 표는 데이터 소스 ID와 칼럼 ID를 저장한다. 차시별 수집 모드는 모든 하위 표에서 이름과 타입이 일치하는 칼럼을 사용한다. 앱에서 여는 주소는 수집 참조와 별도로 바꿀 수 있다.
- 수집 방식은 사용자가 등록한 카테고리 이름과 독립적으로 고른다. 목록은 제목과 선택한 담당자·상태·기한을 사용한다. 일정은 제목과 시작·종료 날짜를 사용하며 원본 분류, 참여자, 취소 여부를 추가로 연결할 수 있다. 차시별 하위 표는 목록에서 사용한다. 기존 소스는 저장된 매핑과 수집 기준을 이어받는다.
- 카테고리의 값 종류는 텍스트·숫자·날짜·시간·참/거짓이다. `columnMappings`에는 원본 속성의 ID와 타입을 소스별로 저장한다. 저장된 이전 연결은 같은 원본 타입을 계속 사용한다. 참여자·상태·선택과 같은 Notion 속성은 텍스트 칼럼에도 연결할 수 있다.
- 시간 칼럼은 서울 시간의 시·분을 표시하며 날짜 전용 값의 시간은 비워 둔다. 날짜 칼럼은 캘린더의 표시 기준으로 사용할 수 있다. 숨긴 칼럼도 날짜와 알림에서 사용할 수 있도록 수집한다. 표시 대상이 바뀌면 정기 수집을 앞당긴다.
- 수집 소스를 저장할 때 등록된 카테고리를 선택해야 한다. 이전 문서에 남은 미지정 소스는 설정에서 수정할 수 있으며, 지정할 때까지 수집·조회·알림에는 사용하지 않는다.
- 사용자가 사람 칼럼을 연결하지 않은 새 소스는 해당 표 전체를 관리자용 메인 화면과 달력에 표시한다. 본인 업무 MCP 조회와 사람 기준 알림은 연결된 사람 칼럼이 있을 때만 사용한다.
- 프로바이더별 스키마 조회와 수집을 별도 계약으로 주입한다. Notion 설정의 칼럼 탐색과 업무 행 수집은 별도 어댑터로 두고, HTTP 요청 간격·커서·하위 표 탐색은 같은 읽기 모듈을 사용한다. 현재 등록된 프로바이더는 Notion이며 기존 문서에 `provider`가 없으면 Notion으로 읽는다. 새 연결과 변경된 매핑은 저장 전에 조회한 스키마로 검증한다. 연결이 바뀌면 다시 시작한 뒤 수집한다.
- 목록과 필요한 상세 속성의 페이지네이션이 끝나야 성공으로 처리한다. 한 행의 속성은 디코딩한 ID로 한 번 색인하고, 역할과 저장 칼럼이 같은 속성을 가리키면 해당 행의 상세 조회 결과를 공유한다. 내장 값이 완전한 단순 제목·사람 목록은 재사용하고 참조 제목과 잘릴 수 있는 속성은 전체 조회한다. 반복 커서·중복·권한·매핑 오류는 부분 성공으로 바꾸지 않는다.
- 일정은 `category`·`eventTypes`로 회의·휴가·기타를 분류하고 `cancelled`로 취소 근거를 저장한다. 잘못된 취소 속성은 미취소로 취급하지 않는다. 휴가 분류와 승인 판정은 별개다.
- 실행권의 세대와 만료를 확인해 오래된 실행의 결과를 막는다. 스테이징 자료와 스냅샷·변경 이력·알림을 함께 확정한다. 수집 실패 시 마지막 정상 자료를 보존하고 처음 누락된 행만 `unconfirmed_missing`으로 바꾼다. 업무 변경 비교에는 이번 수집에 포함된 ID의 이전 원문을 묶어서 읽는다. 누락 후 다시 나타난 업무도 마지막 정상 값과 비교한다. 매핑이 바뀌면 이전 스냅샷을 새 연결에 사용하지 않는다. SQLite 직렬화 모듈에서 소스의 업무 의미를 결정하는 필드만 골라 매핑 해시를 계산한다. 항목은 유형별 저장 필드를 한 행씩 직렬화한다. 비어 있는 선택 칼럼을 생략해 기존 JSON 바이트와 의미 해시를 유지한다.
- 소스별 다음 실행 시각·재시도 횟수는 SQLite에 저장한다. 예약 실행기는 현재 소스의 예약 시각과 실행권 만료 시각을 한 번에 읽는다. 실행할 소스가 없으면 쓰기 트랜잭션 없이 대기한다. 기한이 된 소스는 설정 순서대로 처리하고, 실행권을 얻는 트랜잭션 안에서 기한과 만료를 다시 확인한다. 상태를 조회할 때 최신 실행 이력을 연결해 성공·실패·진행 건수를 집계한다. 수동·예약 명령은 같은 조립부에서 원천, 스냅샷 저장소와 업무·회의 알림 정책을 받는다. 예약 실행에만 도래 시각 확인과 빠른 재시도 정책을 주입한다. 기본 15분이며 `collection_preferences`가 환경 기본값보다 우선한다. 재시작·절전 복귀 시 밀린 예약은 한 번 실행한다. 주기 변경은 예약과 함께 저장하고 진행 중인 실행권을 유지한다.
- 네트워크·시간초과·요청 제한은 15·30·60초 간격으로 최대 세 번 빠르게 재시도한다. 서버의 대기 지시를 반영한다. 인증·권한·매핑 실패는 정기 주기로 돌아간다. 지연 기준은 UI에서 보정한 시각 대신 실제 저장된 다음 예약 + 5분이며 예약 없는 수동 자료에만 최대 유효시간을 적용한다.

## 결과와 검증

사용자는 실패 후에도 마지막 정상 자료와 지연 근거를 볼 수 있다. 보관 확인값은 수집 차단 조건으로 쓰지 않는다. `src/infrastructure/notion/`, `src/infrastructure/sqlite/snapshots.py`, `src/infrastructure/sqlite/schedules.py`, `src/application/periodic.py`에서 구현한다. 임시 저장소에서 차시 일부 실패·실행 중단·정상 복구와 재시도 예산을 확인한다.
