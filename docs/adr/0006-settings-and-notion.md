# ADR 0006. 설정 저장과 Notion 연동

상태: 채택

## 맥락

앱 실행 정보, 화면 선택, 회사별 매핑, 프로바이더 자격 정보는 갱신 주기와 접근 권한이 다르다. 기존 자료를 유지하면서 설정 화면에서 필요한 값만 수정한다.

## 결정

비밀값과 형식 검증, 버전이 있는 저장 레코드, 저장소 포트와 공개 오류 분류는 `src/application/credentials.py`에서 공유한다. Notion의 환경값 복귀, Slack 앱 토큰의 형식, MCP 토큰 발급은 각 유스케이스에서 결정한다.

Notion·Slack 관리 HTTP의 공통 자격 정보 오류는 `src/presentation/credential_errors_http.py`에서 변환한다. `conflict`는 409, `keychain`·`busy`·`unavailable`·`timeout`·`rate_limited`는 503, `invalid`·`missing`·`unauthorized`·`permission`은 422로 반환하며 기존 `detail.code`를 유지한다. 조회·명시적 승인·저장·확인·삭제가 같은 정책을 따른다. 외부 토큰 거부는 로컬 API 관리자 인증의 401·403과 구별한다. Slack 발송 전용 오류는 해당 HTTP 경로에서 별도로 처리한다.

파일 가져오기와 SQLite 읽기·편집은 application의 `parse_settings`로 같은 설정 검증을 수행한다. 수집 소스 화면과 서비스 시작 시에는 같은 읽기에서 얻은 원본 문서와 검증된 매핑을 함께 사용한다. 업무 문서 저장 시 현재 버전을 쓰기 트랜잭션 안에서 다시 확인한다. 이때 읽은 기존 문서와 새로 저장한 문서의 검증 결과를 규칙·구독 비교에 재사용하고, 저장 응답의 재시작 필요 여부는 실제로 확정한 매핑으로 판정한다. 최상위 키·버전과 하위 항목은 Python 타입으로 확인하고, 잘못된 문서는 원문 없이 `WorkSettingsError`로 반환한다.

| 저장 위치 | 값 |
| --- | --- |
| Application Support의 `bootstrap.json` v2 | SQLite 위치, 로컬 포트. 파일 권한 600 |
| SQLite `runtime_settings` | 비밀값 없는 조회 정책, 유효시간, Notion·Slack 계정 식별자 |
| SQLite `work_settings` | 소스 속성 매핑, 페이지 링크, QA 표시, 보관 확인값, 이전 근무 규칙 |
| Application Support의 `work-rules.json` | 근무 규칙 편집값. 파일 권한 600. [ADR 0004](0004-attendance.md) |
| SQLite `app_preferences`, `collection_preferences` | 화면 순서와 표시, 캘린더·알림·발신 앱 선택, 수집 주기 |
| 사용자 Keychain | 앱 내부 관리 키, Notion 토큰, Slack 봇·앱 토큰 |

`src/bootstrap/keychain.py`가 네 계정의 저장 키·표시명·잠금 경로를 정한다. 개발 실행본과 배포 앱의 설치 점검, 설정 편집, 자동 발송이 같은 계정 정의를 사용한다. 메뉴바 시작, 설정 자동 조회와 재시도에서는 승인 창을 띄우지 않는다. 저장된 연동 키에 접근할 수 없으면 사용자가 해당 Notion 또는 Slack 설정에서 `다시 불러오기`를 눌러 그 연동의 키만 승인할 수 있다.

- 일반 설정은 초기화 후 SQLite가 개발용 환경값보다 우선한다. `settings import`와 `settings import-work --file`은 명시적 최초 가져오기다. 기존 업무 문서를 덮지 않고, 이전 링크 선택을 초기 JSON보다 우선한다. 새 앱 설치에는 빈 업무 문서를 준비한다. v1 시작 파일은 호환하며 개인 설정 파일 경로는 사용하지 않는다.
- Notion 설정은 본인 ID·업무 범위와 토큰을 관리한다. `수집 소스`는 SQLite `work_settings` JSON의 `sources`만 버전 검사 후 교체한다. 같은 문서에 있는 근무 규칙과 보관 정책은 유지한다. 수집 연결, 화면 구성, 캘린더 및 알림 설정은 앱 재시작 후 적용하고, 열기 주소와 규칙별 알림 문구·전달 채널은 저장 직후 반영한다.
- `카테고리`는 수집 소스와 독립적으로 등록·수정·삭제한다. SQLite `work_settings` JSON의 `categories`에 이름과 ID를 한 번 저장하고, 각 소스는 `categoryId`만 참조한다. 기존 소스에 내장된 카테고리는 ID와 이름을 유지해 처음 저장할 때 이전한다. 멤버가 없는 카테고리도 남겨 두며, 사용 중인 카테고리는 연결을 해제한 뒤 삭제한다. 이름과 원본 주소만 바뀌면 실행 중인 연결을 그대로 쓴다.
- 서버는 이전 기본 영역에 실제로 연결돼 있던 업무·QA·회의 소스만 같은 이름의 사용자 카테고리로 한 번 이전한다. 카테고리와 기존 표시·알림 선택을 같은 트랜잭션에서 확정한다. 기존 데이터에 등장하는 카테고리 이름·순서·규칙은 해당 사용자의 이전 자료로만 취급한다. 이를 공통 기본값으로 관리하지 않는다. 신규 설치는 카테고리가 비어 있는 상태로 시작하며, 이전이 끝난 뒤 사용자가 비우거나 삭제한 구성도 그대로 유지한다. 이전이 필요한지 읽기 전용으로 확인하고, 필요하면 SQLite 쓰기 잠금 안에서 최신 문서를 다시 읽는다. `application/work_settings_upgrade.py`가 카테고리 배정 → 칼럼 → 이벤트 → 메인 목록 순서와 저장할 버전을 결정한다.
- 예전 소스의 표시 칼럼과 캘린더·알림 설정은 서버 시작 시 카테고리 구성으로 이전한다. 같은 값 종류와 이름의 칼럼은 되도록 공유하고, 기존 원본 연결과 규칙 ID·대상 소스는 그대로 유지한다. 스냅샷은 원본 연결이 동일한 이전 값을 계속 읽을 수 있다.
- 기존 메인 목록 규칙은 서버가 시작할 때 연결된 소스 종류와 해당 사용자의 QA 설정을 읽어 카테고리의 `mainList`에 한 번 기록한다. 한 트랜잭션에서 이전 완료 표시까지 저장해, 이후 추가한 카드나 직접 지운 규칙은 다음 시작에서 채워지지 않는다.
- 분류 버전 2는 설정 준비 트랜잭션에서 각 소스의 기준 칼럼·값별 이름·기본 이름을 저장한다. 이전 카테고리 기준은 실제로 연결된 소스에 복사한다. 공통 기준이 적용되지 않았던 소스는 업무·QA 상태와 명시적 완료값, 일정 유형과 의미 분류, 휴가 승인 상태와 승인값을 각각 사용한다. 데이터 소스를 구분하고 QA 차시의 이름 기반 연결을 유지한다. 기존 판정·알림 조건은 원문으로 계속 평가한다.
- 분류 버전 3은 기존 카드가 상태 그룹을 사용하는 경우, 같은 원본 연결의 스냅샷과 저장된 상태 선택지에서 예전 그룹에 대응하는 이름을 찾아 소스 규칙으로 기록한다. 완료로 선택한 값도 정렬을 위한 그룹과 별개로 보존한다. v2에서 자동 생성한 연결은 보완하고 직접 바꾼 분류·기본값·해제한 연결은 보존한다. 이후 추가되는 값은 소스의 ‘그 밖의 값’ 설정을 따른다.
- 분류 버전 4는 소스의 기존 값별 매핑을 단일 일치 조건으로 이전한다. 규칙마다 여러 원본 칼럼의 조건을 모두 또는 하나라도 만족하도록 설정한다. 위에서 처음 일치한 규칙의 결과를 선택한 칼럼에 표시한다. 빈 비교값은 빈 원본에 일치하고, 어느 규칙도 맞지 않으면 기본 이름 또는 결과 칼럼의 원문을 사용한다. 완료·승인과 알림은 기존 원본으로 판정한다.
- 신규 설정은 빈 카테고리와 수집 소스 목록에서 시작한다. 저장 칼럼의 이름·타입·표시 여부는 카테고리에서 직접 정하고, 수집 소스에서 실제 표의 원본 속성을 연결한다.
- 규칙 편집기는 별도 관리자 조회에서 현재 카테고리에 연결한 선택·상태 칼럼의 수집값을 읽는다. 최신 설정의 소스 매핑·원본 칼럼 연결과 일치하고 유효기간 안에 있는 정상 스냅샷의 값만 칼럼별로 합친다. 행 누락·수집 실패·속성 재연결도 다음 조회에 반영한다. 예전 스냅샷은 상태·분류·승인 역할에서 수집 타입이 확인되는 연결만 바로 제공한다. 다른 선택 칼럼은 다음 정상 수집에서 타입을 확인한다. 응답에는 칼럼당 200자 이하 값 최대 100개, 카테고리 전체 최대 1,000개를 담는다.
- 토큰을 바꾸기 전 `users/me`와 현재 소스의 최소 읽기를 확인한다. 저장된 토큰도 재검사할 수 있다. Keychain은 잠금과 revision으로 교체하고 삭제 표시로 개발 환경의 예전 키가 되살아나는 것을 막는다. 미등록·접근 실패 시 수집을 멈추고 설정 API는 유지한다. 토큰 원문은 화면에 되채우거나 응답·로그에 쓰지 않는다.
- 페이지 링크는 기존 업무·QA·회의 소스의 `pageUrl`만 바꾼다. 빈 값은 링크를 제거한다. 수집 매핑·해시·근무 규칙은 보존한다. 메뉴바 조회 때마다 SQLite에서 현재 버전과 원문을 확인한다. 버전·저장 타입·원문 해시가 모두 같으면 직전에 검증한 링크 목록을 재사용한다. 달라진 문서는 전체 설정을 다시 검증한다. 페이지 링크 버전으로 늦은 조회가 링크를 되돌리는 것을 막는다. 소스 라벨의 팝오버는 현재 속성 매핑과 쓰임새를 설명한다.
- 공통 `notion_link`로 Notion HTTPS 주소를 검증한다. 페이지 ID가 포함된 웹 경로는 앱 페이지 주소로 정규화하며 쿼리·앵커를 보존한다. 캘린더·메뉴바·알림이 이를 재사용한다.

## 결과와 검증

서비스는 시작 파일·DB·Keychain으로 조립된다. 직접 실행하는 CLI에는 환경변수를 명시적으로 주입할 수 있다. `src/bootstrap/app_settings.py`, `work_settings.py`, `src/application/runtime_settings_service.py`, `notion_credentials.py`, `notion_page_links.py`에서 구현한다. 임시 자료로 기존 값 보존, 연결 실패, 충돌, 토큰 삭제와 링크 즉시 반영을 확인한다.

자격 정보 오류는 실제 유스케이스·HTTP와 임시 SQLite·가상 자격 정보 저장소를 연결해 두 확인 경로의 미등록·충돌·일시 장애 및 공개 코드 일치를 확인한다. 개발 앱 PDD는 운영 프로필과 분리한 임시 저장 경로와 고유 루프백 포트를 사용하고, 검사 실패 전후의 저장 자료 보존과 화면 안내를 확인한다. 가상 원천 검증은 실제 회사 연동 검증으로 간주하지 않는다.
