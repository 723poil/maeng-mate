# 0011. 이슈와 PR 관리

## 상태

채택

## 맥락

같은 목록에 수집 실패, 설정 화면의 오류, 기능 제안과 내부 구조 개선이 함께 쌓인다. 작업의 성격과 처리 순서를 별도로 검색할 수 있어야 한다.

## 결정

독립적으로 수정하고 검증할 수 있는 문제 하나를 이슈 하나로 등록한다. 제목에 대상과 바뀌어야 할 동작을 쓰고 본문에는 사용자가 받는 영향, 확인 근거, 완료 기준을 남긴다. 재현한 결과와 코드에서 추론한 가능성을 구별한다.

| 항목 | 적용 기준 |
| --- | --- |
| 유형 | 유형 라벨 하나를 선택한다. 현재 동작의 결함은 `bug`, 기능 추가·개선은 `enhancement`, 동작 보존을 전제로 한 구조 정리는 `refactor`, 문서만 바꾸는 작업은 `documentation`이다. |
| 우선순위 | 아래 표에서 라벨 하나를 고른다. 확정된 영향, 발생 빈도, 우회 가능성으로 판단한다. 구현 난이도는 별도로 고려한다. |
| 작업자 | 착수 전에는 비워 둔다. 착수하는 사람이 자신을 지정하고, 인계하면 다음 책임자로 변경한다. 공동 작업자는 필요한 경우에만 추가한다. |
| 마일스톤 | 포함할 릴리스가 합의된 경우에만 지정한다. P1도 릴리스 약속과는 별개다. |
| 기타 필드 | 선행 이슈가 있으면 본문에서 번호로 연결한다. 접근성·도움 요청 등 기존 보조 라벨은 해당할 때만 추가한다. 별도 Projects 필드는 요구하지 않는다. |

| 라벨 | 작업 순서와 판정 기준 |
| --- | --- |
| `priority:P0` | 현재 배포를 막거나 광범위한 장애·데이터 손상이 진행 중이다. 다른 작업에 앞서 대응한다. |
| `priority:P1` | 핵심 기능이 반복적으로 실패하거나 영속 데이터의 무결성이 위태롭다. P0 처리 후 먼저 착수한다. |
| `priority:P2` | 사용자에게 영향을 주지만 범위가 제한되거나 우회할 수 있다. 일반 작업으로 계획한다. |
| `priority:P3` | 드문 경계값, 경미한 표시 오류, 동작을 보존하는 구조 개선이다. 관련 영역을 변경할 때 함께 검토한다. |

### PR 관리

일반 PR 제목에는 바뀌는 대상과 결과를 적는다. [일반 PR 양식](../../.github/pull_request_template.md)에 변경 이유, 영향, 검증 결과와 관련 이슈를 기록한다. 릴리스 PR은 [배포 ADR](0010-macos-distribution.md)의 제목·호환성·검증 규칙과 [릴리스 전용 양식](../../.github/PULL_REQUEST_TEMPLATE/release.md)을 따른다.

| 항목 | 적용 기준 |
| --- | --- |
| 유형 | 주된 변경을 기준으로 `bug`, `enhancement`, `refactor`, `documentation` 중 하나를 붙인다. 빌드·배포 절차 변경은 `build`, 버전 배포를 위해 모은 PR은 `release`를 사용한다. |
| 담당자·리뷰어 | PR을 열 때 수정과 후속 대응을 맡은 사람을 담당자로 지정한다. 보통 작성자가 맡고 인계하면 변경한다. 리뷰어는 검토를 요청할 사람이 있을 때 별도로 지정한다. |
| 우선순위 | 작업 순서는 연결 이슈의 `priority:P0`~`priority:P3`에서 관리한다. 여러 이슈를 모은 릴리스 PR에서는 개별 이슈의 등급을 참조한다. |
| 마일스톤 | 릴리스 PR에는 대상 버전을 지정한다. 일반 PR도 해당 릴리스에 포함하기로 확정되면 같은 마일스톤을 쓴다. 이미 배포한 버전의 문구를 나중에 고친 경우 제목에 적힌 버전만으로 마일스톤을 붙이지 않는다. |
| 이슈 연결 | 기본 브랜치 병합으로 해결할 이슈는 본문 끝에 `Closes #번호`로 연결한다. 릴리스 브랜치로 먼저 병합할 때는 일반 PR에 관련 번호를 남기고, 기본 브랜치로 가는 릴리스 PR에 종료할 이슈를 적는다. |
| 진행·검증 | 검토 준비 전에는 Draft를 쓴다. 실제 수행한 검증 결과와 남은 수동 확인을 구분하고, 커밋이 추가되면 본문을 갱신한다. 종료된 PR에는 확인 가능한 메타데이터만 소급 적용한다. |

## 결과와 검증

웹에서는 저장소의 이슈 양식을 사용한다. CLI나 에이전트도 같은 본문 항목을 작성하고 생성할 때 유형·우선순위 라벨을 붙인다. 웹 양식은 라벨을 자동 적용하지 않으므로 등록자 또는 분류 담당자가 실제 라벨까지 확인한다.

작업을 고를 때 열린 이슈를 P0부터 확인한다. 같은 등급에서는 다른 작업을 막는 문제, 다음 릴리스에 포함하기로 한 문제, 먼저 등록한 문제 순서로 본다. 영향이나 재현 조건이 바뀌면 기존 우선순위 라벨을 교체하고 이유를 한 줄 남긴다. 완료 시 본문의 검증 기준과 구현 결과를 연결하고 이슈를 닫는다.
